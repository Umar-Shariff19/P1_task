# Phase S — bounded static entrypoint and access-boundary audit

**Status:** source review only; none of the listed entrypoints was executed. No dataset/checkpoint files were inspected. This is a systematic bounded scan, not an exhaustive proof of every dynamic call path.

## Scope and method

- Enumerated Python source paths only under `scripts/` and `src/`: 150 `.py` files at review time. Tests, generated outputs, datasets, checkpoints and candidate checkout were excluded from discovery.
- Read the project console-script declarations in `pyproject.toml` (`p1-audit-datasets`, `iot-ids`). Searched the 150 source files for `if __name__`, `def main`, `argparse` subparsers, app decorators, subprocess calls, file readers/writers, `glob`/`rglob`/`os.walk`, `.fit()`, checkpoint loaders and capture calls.
- The static markers found 55 Python files with a `main` or module-main marker (53 under `scripts/` and 2 under `src/`). The I/O/training signature search matched 78 files. Direct scripts without a guard can also execute module-level work.
- Inspected dispatcher, CLI, dataset audit/adapters, materialization/split scripts, major training/evaluation/benchmark runners, model loaders, and broad-walk packaging scripts as source text. No AST/call-graph tool or runtime trace was used.
- Search limitations: aliased/dynamic imports, reflection, library callbacks, dynamically constructed paths, `Path.read_text/read_bytes` not covered by every search pattern, and entrypoints outside `scripts/` and `src/` may not be captured. Thus this report makes no exhaustive claim. All direct script invocation remains a potential bypass until centrally enforced at each data/model access API.

## Concrete bypass and ordering findings

1. `run_master.py` is an orchestrator, not a security boundary. It launches child paths directly and does not validate a manifest or policy. A user can invoke the same children without the orchestrator.
2. `src/iot_ids/data/audit.py:run_audit()` creates its output directory before adapter audit, and the adapter base calls discovery itself. A future gate only in `scripts/audit_datasets.py` would not protect importable `run_audit()` or `.audit()` calls.
3. `scripts/03_materialize_and_audit_features.py` instantiates adapters and calls stream methods without any shared authorization object. Several other scripts bypass it by reading parquet directly.
4. Split readers and checkpoint loaders are distributed across the direct scripts and library APIs shown above. A single CLI/dispatcher gate cannot cover these direct imports and paths.
5. `build_p1_task_implementation_zip.py` recursively walks a runtime-selected repository root. This is a separate broad-read risk: never run it as a shortcut for provenance inventory. The package/hash scripts are not authorization-aware either.
6. No reviewed entrypoint validates the prospective experiment schema, verifies an owner signature, checks an OS filesystem identity, or invokes the Phase R coordinator. A matching hash in a script or manifest cannot authorize access.

## Safety-helper claims checked against code

| Helper | Supported behavior | Unsupported guarantees / risks |
|---|---|---|
| `src/iot_ids/data/path_policy.py` | Pure lexical parsing of local absolute Windows-looking paths; rejects UNC/device namespace, parent components and selected ambiguous names; component-wise case-folded deny overlap; exact spelling allow match; refuses absent verifier. It performs no filesystem query. | `RootIdentityEvidence`, verifier, policy and returned root are caller-constructible. It cannot establish that a drive letter maps to a volume, resolve junction/symlink/mount aliases, verify per-directory case behavior, or hold a handle. No adapter uses it. It is not filesystem authorization. |
| `manifest_validation.py` | Uses a fixed repository schema; Draft 2020-12 validation; rejects external/dynamic reference keywords; returns generic schema/dependency errors; auth/evidence booleans stay false. Schema validation is independent from authorization. | It validates recorded structure, not approval authenticity, run occurrence, truth, source revision, or split provenance. The repository schema itself is a local file read. |
| `artifact_integrity.py` | Accepts one explicit relative file under a caller-supplied absolute base; validates SHA-256; lexical escape rejected; `lstat` on each named component rejects observed symlink/reparse entries and non-regular final objects; hashes bytes of the explicitly named file only. | `base.resolve(strict=True)` resolves/follows the caller-supplied base and is not authorization. Check-then-open has a TOCTOU window: components can change after `lstat` and before `candidate.open()`. A hard link can name unintended content inside the base; link identity/count is not checked. Windows path identity/case semantics and handle binding are not proved by `relative_to()`. Direct helper errors preserve chained OS exceptions, which may reveal paths in a traceback. Synthetic-only use remains appropriate. |
| `preflight.py` | Schema is checked first; missing/denied/indeterminate/malformed authorization blocks; only `SYNTHETIC_ONLY` can yield `READY_SYNTHETIC`; `REAL_DATA` is always rejected; required/mismatching/missing/invalid artifact evidence blocks. Result categories omit raw exception text/paths and evidence remains `UNVERIFIED`. | `AuthorizationDecision`, `PreflightResult`, and provider objects are ordinary Python values. An arbitrary injected provider can fabricate a synthetic decision; the coordinator trusts that policy boundary. It cannot bind real authorization to OS identity and is not an execution lock/handle. A caller can forge `READY_SYNTHETIC`; no production access function consumes it. It is not integrated into runners/adapters. |

Artifact handling should not be promoted from synthetic tests to real artifacts until the OS-bound context replaces path-based check-then-open. The Phase I and Phase J incidents remain unresolved; this audit supplies no incident evidence.
